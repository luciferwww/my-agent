# Session Management Specification

> Status: Implemented and Validated
> Date: 2026-09-18
> Owner: Project owner
> Related Plan/Decision: [Session Identity and Management Plan](plan.md), [ADR-015](../../../decisions/adr-015-session-identity-and-materialization.md)
> Authorization: Accepted contract; delivery approved by the project owner on 2026-09-18

## Purpose and observable outcome

Clients create, locate, rename, archive, delete, fork, resume, and stop Sessions through one immutable server-issued `sessionId`. Creating a Session does not persist an empty resource. The first accepted message materializes the Session and makes it visible in list/get operations.

## Scope

- Session metadata, Store layout, and Transcript location.
- Pending Session registration and first-message materialization.
- Session management and message-admission contracts.
- Session lifecycle, runtime status projection, errors, concurrency, and recovery.
- Session identity used at Store, Runtime, and Channel boundaries.

## Non-goals

- Reading or converting pre-cutover Session data.
- Multi-process access, cloud synchronization, or distributed locks.
- LLM-generated titles.
- Transcript message-tree, Compaction algorithm, Provider-history, or consumer-internal redesign beyond the identity and metadata adaptations directly required by this contract.
- Detailed CLI/TUI visual design.

## Boundaries and dependency direction

The target ownership is:

```text
Channel / Host
  -> Runtime Session coordinator
        -> PendingSessionRegistry
        -> SessionManager
    -> Runtime Session-scoped execution
```

- `SessionManager` owns persisted metadata, Transcript files, message-tree operations, and persisted lifecycle changes.
- The Runtime Session coordinator owns ID reservation, Pending policy, operation validation, and first-message materialization orchestration.
- Runtime owns Turn admission, per-Session serialization, queues, Abort, steering, and live status. It does not implement title or Store rules.
- Channels and Hosts expose Session operations and pass canonical IDs. They do not read `sessions.json` or access the Pending Registry directly.
- Session storage is local to one `agentHome`. The first contract has no separate scope property or cross-`agentHome` lookup.

## Public and structural contracts

### Session metadata

```ts
interface SessionEntry {
  sessionId: string;
  title?: string;
  createdAt: number;
  updatedAt: number;
  archivedAt?: number;
  forkedFromSessionId?: string;
}

interface UpdateSessionInput {
  title?: string | null;
}

interface SessionStore {
  version: 1;
  sessions: Record<string, SessionEntry>;
}
```

Invariants:

- `sessionId` is a canonical UUID generated by the service and never changes.
- Every `sessions` key equals its entry's `sessionId`.
- `title` is optional and non-unique. `null` clears a title; a string must contain non-whitespace text after trimming.
- `createdAt` never changes. `updatedAt` advances after a successful metadata or Transcript mutation.
- `archivedAt` records persistent archive state and is unrelated to live Runtime status.
- `forkedFromSessionId` identifies the direct source of a persisted fork only.
- Update operations cannot accept identity, timestamps, path fields, or arbitrary partial metadata.

### Prior metadata disposition

The new Store does not retain the prior `sessionKey`, `sessionFile`, `status`, `abortedLastRun`, `totalTokens`, `inputTokens`, `outputTokens`, `compactionCount`, or `spawnedBy` fields.

- Identity and path fields are replaced by canonical `sessionId` and derived Transcript location.
- Live status remains Runtime-derived rather than persisted.
- Compaction statistics remain authoritative in existing `CompactionRecord` values; removing redundant Session summary fields does not change Compaction selection, retained history, or Provider input.
- Last-run and usage summaries are outside the first Session metadata contract. Reintroducing one requires an explicit contract amendment with an owning source of truth.
- Session consumers adapt only their Session identity and metadata calls. Their unrelated execution and event behavior remains outside this Change.

### Files

```text
<agentHome>/sessions/
├── sessions.json
└── <sessionId>.jsonl
```

- Transcript location is derived from `sessionId`; metadata does not store a filename.
- `sessions.json` uses the exact `SessionStore` wrapper above.
- An invalid version, invalid UUID, key/entry mismatch, invalid parent reference, or structurally invalid entry is a Store data error.
- The pre-cutover directory must be empty. No previous Store schema is accepted.

### Pending registration

```ts
interface PendingSessionRegistration {
  sessionId: string;
  createdAt: number;
}
```

The proposed first-contract policy is:

- TTL: 30 minutes from `createdAt`.
- Capacity: 4096 live registrations per process.
- Cleanup: lazily remove expired registrations before create and Pending lookup; no timer or background resource.
- Capacity exhaustion: after cleanup, reject creation with `SESSION_CAPACITY_EXCEEDED`; do not evict an unexpired registration.
- Expiry: an expired ID behaves as unknown and returns `SESSION_NOT_FOUND`.
- Restart: all Pending registrations disappear and their IDs are no longer usable.

The clock and policy are injectable for deterministic tests but are not first-contract user configuration.

### Runtime Session coordinator

```ts
interface SessionCoordinator {
  createSession(): Promise<{ sessionId: string }>;
  listSessions(input?: { archived?: boolean }): Promise<SessionEntry[]>;
  getSession(sessionId: string): Promise<SessionEntry>;
  renameSession(sessionId: string, title: string | null): Promise<SessionEntry>;
  archiveSession(sessionId: string): Promise<SessionEntry>;
  unarchiveSession(sessionId: string): Promise<SessionEntry>;
  deleteSession(sessionId: string): Promise<void>;
  forkSession(sessionId: string, entryId?: string): Promise<SessionEntry>;
  sendMessage(input: SendMessageInput): Promise<AcceptedTurn>;
  stopSession(sessionId: string): Promise<StopResult>;
}
```

The exact transport encoding may differ, but its semantics and field names must match this contract. `SendMessageInput`, `AcceptedTurn`, and `StopResult` retain their owning message/Runtime fields while replacing Session identity with `sessionId`.

The implemented stop encoding retains its existing Runtime owner: `RuntimeApplication.abortTurn(sessionId)` returns the `StopResult`, WebSocket exposes `abort_turn`, and CLI Ctrl+C invokes the same capability. There is no duplicate Session-coordinator stop path.

## Behavior and invariants

### Create and visibility

1. `createSession()` generates a UUID, records `{ sessionId, createdAt }` in memory, and returns the ID.
2. It does not create `sessions.json`, a Transcript, or a list/get result.
3. `listSessions()` returns persisted, non-archived Sessions by descending `updatedAt`, then `sessionId` ascending as a deterministic tie-breaker.
4. `listSessions({ archived: true })` returns archived Sessions only. The first contract does not provide an all-states mode.
5. `getSession()` returns persisted Sessions regardless of archive state. Pending IDs return `SESSION_NOT_FOUND`.

Selecting “new Session” is a client-local state transition and does not call `createSession()`. The CLI must defer creation until the user submits the first message, then create and immediately send with the returned `sessionId`. WebSocket clients should follow the same policy by issuing `create_session` only when submitting the first message and then issuing `run_turn`; the WebSocket Channel does not implicitly create a Session for `run_turn`.

### Initial title

On first materialization, the service derives a title from the first non-empty user-authored text block:

1. ignore attachments, injected system text, and Tool Results;
2. trim and collapse contiguous whitespace to one space;
3. segment by Unicode grapheme cluster;
4. store at most 48 graphemes, using one ellipsis grapheme within that limit when truncated;
5. leave `title` absent when no usable text exists;
6. never call an LLM and never fail materialization solely because title derivation fails.

Rename is explicit metadata input, not auto-title derivation. `null` clears the title. A non-null title is trimmed and rejects an empty result with `SESSION_TITLE_INVALID`; internal characters otherwise remain caller-controlled.

### First-send materialization

`sendMessage()` enters the Runtime's per-`sessionId` gate before inspecting persistent or Pending state.

- Persisted, non-archived Session: append through the normal Turn path.
- Persisted, archived Session: reject with `SESSION_ARCHIVED`.
- Store miss and live Pending hit: materialize and then accept the Turn.
- Store miss and Pending miss/expiry: reject with `SESSION_NOT_FOUND`.

Materialization uses this commit protocol:

1. Derive the initial title from the admitted message and construct a Transcript containing only the Session root.
2. Write and close a same-directory temporary Transcript.
3. Atomically rename the temporary Transcript to `<sessionId>.jsonl`.
4. Atomically replace `sessions.json` with a Store containing the new entry. This Store replacement is the visibility commit point.
5. Publish in-memory Transcript state and remove the Pending registration only after the Store commit succeeds.
6. Return or emit the accepted Turn containing `turnId` only after the Session is committed.

Materialization reads the admitted message only to derive title metadata; it does not append that message to the Transcript. The Runner remains the sole user-message writer and preserves its existing ordering: preflight first, then append the current user message, then invoke the Provider. A Runner failure before append may therefore leave a valid zero-message Session created by an attempted send. This is distinct from an abandoned create flow: a Pending ID that never receives a send remains invisible and creates no persistent resources.

### Transient Subagent Transcripts

A blocking Subagent Child receives a canonical UUID `sessionId` and a Transcript, but it is not a persisted Session resource:

- its Transcript uses the existing `<agentHome>/sessions/<sessionId>.jsonl` location;
- it has no `sessions.json` entry and is therefore absent from Session get/list and CRUD operations;
- its root record carries only `{ type: 'subagent', callerSessionId }` provenance;
- creation writes only that root record; its Runner appends the Child prompt through the normal user-message path;
- while registered in-process, existing message, history, and Compaction operations accept its `sessionId`;
- Runtime deletes it when Child execution terminates, including error and abort paths;
- startup orphan cleanup removes a Transcript left by process termination because it has no Store entry.

This contract does not add Subagent Session listing, recovery, archive, rename, fork, or a second Store schema.

If any step before Store commit fails:

- no Store entry is visible;
- the Pending registration remains live;
- temporary or final unindexed Transcript artifacts are removed best-effort;
- a same-process retry removes or replaces an unindexed artifact only after validating that its filename is the reserved `sessionId` path;
- process startup removes temporary Transcripts and final Transcript files that have no matching valid Store entry.

If Store commit succeeds, failure to remove the in-memory Pending entry cannot invalidate the Session; persisted Store state wins on subsequent lookup and stale Pending state is removed lazily.

No claim of atomicity is made across the Transcript and Store files. Instead, Store visibility plus deterministic orphan cleanup provides recoverable materialization.

### Archive, delete, fork, and stop

- Rename is allowed while a Session is active because it does not affect execution identity.
- Archive, delete, and fork require no active Turn and no queued message. Otherwise they return `SESSION_BUSY`.
- Archive sets `archivedAt`, advances `updatedAt`, rejects future messages, and retains metadata and Transcript.
- Unarchive clears `archivedAt` and advances `updatedAt`.
- Delete removes Transcript and metadata. A Session with a persisted fork descendant returns `SESSION_HAS_DESCENDANTS`; there is no implicit cascade.
- Fork validates the source entry, copies the selected linear history into a new Transcript, creates a new UUID and Store entry immediately, records `forkedFromSessionId`, and copies the source title unchanged when present. A fork is persisted because it already contains history.
- Stop aborts the active Turn and drops queued messages through Runtime behavior but does not archive or delete the Session. Stopping an idle Session is an idempotent no-op result.

## Session lifecycle and runtime status

Persistent lifecycle:

```text
Pending --first committed message--> Active <--> Archived
                                      |
                                      +--> Deleted
```

- Pending is process-local and is not a persisted Session state.
- Deleted is terminal for that `sessionId`; IDs are never reused.
- Live status is computed by Runtime as `idle`, `running`, `waiting_for_input`, `waiting_for_permission`, or `stopped` and is not stored in `SessionEntry`.
- Last-run failure, Abort, usage, and Compaction statistics are not part of the first Session metadata contract. Existing owners may continue to persist their own data only if it does not become Session identity or violate the new Store schema; any retained fields require explicit Specification amendment before acceptance.

## Failure, Abort, deadline, and concurrency semantics

### Errors

| Code | Meaning |
|---|---|
| `SESSION_NOT_FOUND` | ID is neither persisted nor a live Pending registration for the requested operation |
| `SESSION_ARCHIVED` | A new message targets an archived Session |
| `SESSION_BUSY` | Archive, delete, or fork targets a Session with active or queued work |
| `SESSION_HAS_DESCENDANTS` | Delete targets a Session with persisted fork descendants |
| `SESSION_TITLE_INVALID` | Rename supplies a non-null title that becomes empty after trimming |
| `SESSION_CAPACITY_EXCEEDED` | Pending capacity remains full after expired entries are removed |
| `SESSION_DATA_INVALID` | Persisted Store or Transcript identity structure violates this contract |
| `SESSION_PERSISTENCE_FAILED` | A required Store or Transcript operation fails without committing visibility |

- Error transport must preserve the stable code and may add a bounded human-readable message.
- Unknown IDs never create resources implicitly.
- Abort is a Runtime operation and does not roll back already committed Session metadata or Transcript records.

### Concurrency

- Lookup, first materialization, and normal first-send admission for one `sessionId` occur under one per-Session gate.
- Concurrent first sends for one Pending ID materialize at most once. Later contenders observe the persisted Session and enter normal serialized Turn handling.
- Different Session IDs may execute concurrently.
- Store replacement is serialized process-wide or by the Store path so concurrent metadata mutations cannot lose updates.
- Transcript appends remain ordered per Session.
- Multi-process writers are unsupported.

## Security and capabilities

- Callers cannot select a new Session ID; only `createSession()` issues one.
- An arbitrary syntactically valid UUID has no authority and returns `SESSION_NOT_FOUND` unless persisted or Pending in this process.
- This contract does not introduce tenant authorization. Hosts that cross trust boundaries must authorize Session operations before invoking the application service.
- Titles and error messages are data, not path components.
- Transcript paths are constructed from validated UUIDs and never from titles or caller-provided filenames.

## Compatibility and migration

- Required cutover state: `<agentHome>/sessions/` is empty.
- Prior `sessions.json` and Transcript formats are unsupported.
- No migration reader, fallback, dual-write, feature flag, or Compatibility namespace is created.
- All in-scope callers migrate before the old Session identity path is deleted.
- Current Architecture remains authoritative until implementation is validated and documentation authority is transferred.

## Acceptance and validation

### Unit and contract

- Store accepts only version 1 and matching canonical IDs.
- Duplicate titles are allowed; identity/path fields cannot be updated.
- Pending create is invisible and creates no files.
- Expiry and capacity policies are deterministic under an injected clock.
- First-send admission materializes metadata once and preserves Pending `createdAt` without persisting message content.
- Unicode grapheme title derivation, truncation, no-text input, and failure fallback behave as specified.
- Unknown and archived IDs reject message admission with stable codes.
- Fault injection at every materialization write boundary leaves no visible partial Session and permits defined retry or startup cleanup.
- The Runner appends the first admitted user message exactly once after preflight, and that message appears exactly once in the Provider input assembled for its Turn.
- A blocking Subagent Transcript starts with root provenance only, is usable by its Runner, never appears in Session get/list results, and is removed after terminal cleanup or subsequent startup recovery.
- Archive/unarchive, idle requirements, fork copying, and descendant delete restriction behave as specified.
- Prior Session metadata fields are absent; existing Compaction behavior reads its authoritative Transcript records without the removed summary fields.

### Runtime and integration

- Same-Session Turns remain serialized and different Sessions remain concurrent.
- Stop targets only the requested Session and preserves persisted history.
- Session-scoped requests, responses, events, Abort, queues, steering, and audience routing use `sessionId`.
- At least one CLI flow and WebSocket flow exercise create, first send, list/get, rename, and delete.
- No approved Session boundary silently creates an unknown ID.

### Delivery gate

- Focused checks run immediately after each implementation slice.
- Relevant Integration and Fitness suites run after focused checks pass.
- `npm run lint` and `npm run build` pass.
- Full regression commands require explicit project-owner approval after focused implementation and review fixes.
- Independent review verifies no old Store reader, dual identity, unrelated consumer redesign, or undocumented compatibility path remains.

## Review decisions

Accepted on 2026-09-18:

1. one `agentHome` scope with no first-contract scope field;
2. Archive in the persistent/API contract with UI allowed to follow later;
3. idle-only archive/delete/fork;
4. descendant delete restriction without cascade;
5. 30-minute Pending TTL, 4096 capacity, and lazy cleanup;
6. Store replacement as visibility commit point and orphan cleanup as recovery;
7. no old-format migration or feature flag.

These decisions are accepted. Production implementation remains unauthorized until the project owner separately approves Delivery.
