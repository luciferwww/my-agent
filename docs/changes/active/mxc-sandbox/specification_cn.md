# 基于 MXC 的工具执行

> 状态：草案
> 日期：2026-11-23
> 修订：2026-11-24
> 负责人：项目负责人
> 相关计划：[MXC 沙箱采用计划](plan.md)
> 就绪状态：限定范围的 [MXC Spike](spike-specification.md) 已暂时通过；仍需负责人接受设计与迁移方案

[结果](spike-results.md)现已包含 Node 24 SDK、常规离线 npm 任务和元数据边界验证，以及受隔离约束的私有 TEMP 引导程序。
默认设计候选方案是在 Node 24 LTS 上使用公开的进程内 Node SDK V1，
显式授予仅目录枚举的元数据访问权限，并使用一个小型可信 Node 引导程序。
这些是有证据支持的提案，不代表生产方案已获接受。

## 目的与可观察结果

引入可选的 Windows 原生沙箱 `exec` 执行能力，并提供明确且经过验证的文件与网络边界。
命令仍使用正常的工具审批和进程生命周期。当无法建立所请求的隔离时，
应报告失败，而不是在宿主环境执行。

MXC 是选定的技术方向，并非已经验证完成的集成。
本草案既不新增权限模式，也不承诺支持任意命令、工具链或 Windows 版本。

## 范围

- 首个生产候选方案：对 `exec` 及其后代进程实施沙箱隔离，包括前台、yield 和后台模式。
- 负责人选择的工作目录模型：在原始 `cwd` 中操作，
  文件内容写入仅限可信配置路径和自有临时数据。
  不自动复制项目、重映射路径或回写。
- 首个策略候选方案：开放必要的工具与运行时可读路径以及配置的数据路径；
  不自动授予 Agent 数据或凭据访问权限；
  禁止外部网络，包括宿主回环网络。
  目录元数据可见性与文件内容权限保持独立。
- 测量沙箱内的目录列举和文件读取，作为未来文件工具可行性的探测，
  而不是生产文件服务设计。

## 非目标

不包含 Smart Approval、本地分类器、自动授权、公开文件代理协议、
Extension 迁移、三平台推广、网络代理、凭据转发，
或新的沙箱后端选择框架。
不提供自动工作副本、Git worktree、补丁应用、备份或回滚服务。

允许写入的项目文件仍可能被覆盖或删除。
用户可以自行准备一次性副本并将其选为 `cwd`，
但沙箱不会创建或同步该副本。不得将访问约束描述为恢复能力。

Agent 宿主仍在沙箱外。对 `exec` 实施沙箱隔离，
不会使宿主直接进行的文件系统与网络操作受到操作系统级约束。

## 边界与依赖方向

- **Core Tools/Framework：** 保留可移植的工具、验证、执行和闭合契约；
  不依赖 MXC 或平台专用 SDK 类型。
- **Runtime 策略与交互：** 保留审批决策、经 Hook 转换后的有效输入、
  Session/Turn/call 关联，以及首次终结生效规则。
  沙箱成功不得绕过审批或代表用户决策。
- **Builtins 执行：** 将可信执行约束转换为选定的 MXC 绑定，
  并负责工作负载输出、就绪状态与终止集成。
- **现有 ProcessRegistry：** 保留托管进程的所有权、可见性、
  Session 作用域、容量、交接和关闭行为。不引入第二个注册表。
- **Builtins Environment：** 负责沙箱叶级契约、默认值与验证、
  策略编译、SDK 绑定，以及私有的每次执行临时资源。
- **Platform Configuration：** 将该叶级配置组合到全局 `agents.sandbox`；
  保留现有命名空间和不可变投影机制。
- **Runtime 组合：** 将启动时解析的沙箱配置传给 Environment 贡献单元。
  不新增配置文件读取器或每 Agent 覆盖项。

当前边界见[工具契约与策略](../../../architecture/tools.md)和
[内置工具](../../../architecture/builtin-tools.md)。
具体基线是
[run-command.ts](../../../../src/builtins/tools/environment/process/run-command.ts)、
[exec-types.ts](../../../../src/builtins/tools/environment/process/exec-types.ts)
和 [exec-tool.ts](../../../../src/builtins/tools/environment/process/exec-tool.ts)。

## 公开与结构契约

### 启动配置提案

新增全局、通过文件配置的 `agents.sandbox`，
而不是工具参数或 Session 权限模式。初始解析后的结构为：

```typescript
interface SandboxConfig {
  readonly enabled: boolean;
  readonly readonlyPaths: readonly string[];
  readonly readwritePaths: readonly string[];
  readonly deniedPaths: readonly string[];
}
```

默认值为 `enabled: false`，各配置路径列表为空。
启用时在 Windows 上选择 MXC；首个配置档始终禁止外部网络，
不提供网络开关、替代后端或非沙箱重试。

所有路径均为具体的本地绝对路径，而非 Shell 字符串或 glob。
已识别字段中的无效值通过现有 Platform 路径报告机制使配置验证失败。
首个切片不接受 UNC/设备策略根路径、每 Agent 沙箱覆盖项，
或环境变量配置覆盖项。

配置仅在启动时生效。文件变更需要重启；
现有 Settings 分区编辑必须保留该配置，
但不得展示实时开关，或将已保存值标记为已经执行生效。
首个切片不包含浏览器沙箱编辑器和实时重配置。

关闭时保留现有宿主直接执行行为，避免加载或探测原生 MXC。
开启时在 Environment 启动阶段导入并探测；
若所需 Windows 后端不可用，则启动失败，
并在启动每个实际请求前进行检查。
不得静默关闭标志、移除 Exec 或切换后端。

配置示例：

```json
{
  "agents": {
    "sandbox": {
      "enabled": true,
      "readonlyPaths": ["C:\\tools\\shared-runtime"],
      "readwritePaths": ["C:\\work\\project"],
      "deniedPaths": ["C:\\work\\project\\private-data"]
    }
  }
}
```

将配置路径与明确需要的运行时/操作系统读取路径、
执行卷元数据授权，以及每个命令自有的临时路径共同编译。
不得使用会自动授予 HOME、凭据文件或可写共享缓存权限的宽泛开发者配置辅助函数。
新增 `cwd` 或修改 `env.PATH` 不会自动授予更多文件内容访问权限。

原生策略必须能够按照文档所述的 MXC 路径/别名优先级表达配置限制；
对不支持或相互冲突的请求应拒绝，而不是静默丢弃 deny。
集成测试应验证示例中可写项目下嵌套的拒绝访问数据。
应报告隐式操作系统基线访问权限，
而不是声称显式路径列表就是全部可访问文件系统。

### 选定的绑定候选方案

在受支持的 Node 24 LTS 运行时使用 `@microsoft/mxc-sdk/v1`，
初始采用已测试的 SDK `1.1.0`。
SDK 文档要求 Windows 原生标准输入输出至少使用 Node 24.21.0；
Spike 使用了 24.22.3。
默认不新增 .NET 辅助程序或原生 CLI 生产回退方案。

通过 SDK 的 `spawn`、标准流、`wait`、`kill` 和 `dispose`
转换私有执行器契约。
SDK spawn 建立的是沙箱根进程，而不是最终用户命令就绪状态。
直接命令 Spike 验证了真实操作系统 PID；
采用受隔离约束的引导程序时，该 ID 属于可信 Node 根进程。
保留此 ID 用于 SDK 所有权，
且仅在可信引导程序发出启动帧后报告实际 Shell PID。
类型化启动拒绝和引导失败不得发布成功的后台调用。

SDK 的 spawn 选项不接受仓库的执行 AbortSignal。
最小适配器必须通过显式终止句柄，
保留启动前检查、异步启动期间的取消和现有所有权转移。
不得引入相互竞争的注册表或截止时间所有者。

### 元数据与内容访问

已测试的 Windows 候选方案为执行卷添加 `enumeratePaths`，
同时保持文件内容授权不变。
这允许常规 Node/npm 元数据遍历，而不授予整盘文件读取权限，
但后代目录元数据也会变得可查询。
策略、配置和 UX 必须区分这一点与仅工作区可见性。
2026-11-24，负责人明确表示，枚举工作区外目录和读取明确允许的外部文件，
属于预期沙箱行为，不构成采用阻碍。
目标是访问控制，而不是让工作目录之外的所有路径不可见。

保留已测试的仅元数据候选方案；这一澄清不增加文件内容授权。
有效策略可以允许读取外部工具/运行时文件，
但未经授权的内容读写和显式拒绝路径必须仍受约束。
应如实报告隐式操作系统访问权限，
而不是承诺所有外部文件都不可读。
目录名称可见性仍是已记录的能力边界，
而不是尚未解决的兼容性缺陷。

初始候选方案保留现有工具输入与结果。
隔离约束由可信宿主配置决定，
而非模型提供的命令参数或解释。

执行绑定在语义上必须提供：

- 仅在隔离约束建立且目标启动后才进入就绪状态；
- stdout/stderr、退出状态和明确的执行失败；
- 幂等的工作负载树终止，以及最终资源释放；
- 在 yield/后台交接后仍保有所有权的句柄；
- 足够的实际后端/能力信息，以检测未满足的约束。

### 私有命令控制提案

保留 `runCommand` 作为 Builtins 前台和托管执行入口。
其结果保留一个 started Promise 和单一 completion Promise，
但用私有终止控制替代跨调用方的 `ChildProcess` 依赖。
宿主直接执行和 MXC 路径暴露相同语义的 `terminate(reason)` 操作；
仅宿主直接执行实现调用现有进程树终止辅助函数。
MXC 实现通过活动 SDK 句柄终止，而非通过基于 PID 的宿主信号终止。

在异步启动前创建控制，使处于 `starting` 状态的托管记录
已经拥有待启动取消操作。
仅在 SDK spawn、引导程序确认 Shell 启动以及最终取消检查完成后，
才完成 started；在 wait 前连接流。
将该控制存储在现有 ProcessRegistry 中，
替换基于 `child` 的清理路径和 Process Tool 的直接 kill 调用。
无需公开工具 schema、新注册表或 Core SDK 依赖。

在可获得真实操作系统 PID 时继续展示，
但不得将该 PID 作为释放 SDK 策略/原生资源的权威依据。
不得将 SDK 句柄强制转换为 `ChildProcess`、虚构 PID，
或从辅助程序输出推断目标就绪状态。

## 行为与不变量

1. 保留 Hook 转换、schema 验证、策略、审批和 Framework 顺序。
   将审批和执行绑定到同一有效调用。
2. `manual` 保留每次 Exec 调用审批。
   `allow_all` 继续授权未被拒绝的调用；
   授权不会关闭明确选择的沙箱。按工具名称拒绝仍具有最终效力。
3. 三种 Exec 模式使用同一强制执行策略。
   失败不得触发隐藏的宿主直接执行重试或较弱沙箱级别。
4. 保留 Windows `cmd.exe /d /s /c` 语义。
   不替换为 Linux 执行，也不重写 Shell 字符串来重定向任意绝对路径。
5. 保留现有相对于 Agent Home 的 `cwd` 解析。
   解析后的目录是实际执行目录，不是权限授权或自动复制目的地。
   现有文件工具和 Exec 看到同一项目。
   超出允许视图的命令应失败，不隐式增加访问权限。
6. 可写路径来自可信配置，而非 Agent 解释、命令审批或 `cwd`。
   Agent Home 不会仅因是默认相对路径锚点就自动可写。
7. 仅报告真实输出和活动。
   隔离失败是执行失败，而非虚构的用户拒绝或策略模型输出。

## 生命周期与资源所有权

在报告工作负载运行中或发布后台 `runId` 前，
必须完成启动和策略验证。
探测成功仅供参考；启动仍可能失败。
部分启动失败必须终止任何已拥有的工作负载并释放句柄。

前台执行保留调用 Abort 所有权。
成功的 yield/后台交接将活动工作负载句柄转移给现有 Process 所有者；
完成工具调用不得 dispose 已交接的沙箱。

终结仍遵循单一胜者规则。
超时、Abort、手动 kill、Session 删除和 Host 关闭
必须终止实际工作负载及后代进程，
排空输出或明确限制输出排空，
并释放原生句柄和自有临时资源。
仅有辅助程序 PID 不足以构成终止契约。

立即后台调用在成功交接前保留其启动 Abort 所有权；
yield 调用在提升为托管执行前保留该所有权。
这有意关闭当前后台启动缺口：
现有立即后台路径没有将 Parent Abort 传给启动过程。
已取消的待启动操作不得稍后发布成功的 `runId`。

启动期间保持托管记录为内部状态，
仅在成功交接后对外暴露。
提升前检查完成状态与 yield/Abort 的竞争。
根命令退出时，SDK 终止还会移除剩余后代进程；
独立运行的服务器必须保持其根命令存活，
不能期望子进程在根命令完成后继续存活。
应记录这一有意的、仅沙箱模式存在的生命周期差异。

正常终止时，调用 SDK kill，
并在释放和临时清理前观察 wait/流终结。
对终态句柄进行幂等 dispose；
对活动句柄 dispose 不能代替清理完成证明。
清理失败时保留所有者并报告失败，
而不是将记录标记为已清理或删除。

## 失败、Abort、截止时间与并发语义

- 不支持的宿主、请求、产物或绑定：
  在目标执行前明确失败，提供有用原因，不提供形似成功的回退。
- 启动前或启动期间 Abort：
  不留下存活工作负载，不发布后台记录。
- 超时/kill 与自然退出竞争：
  保留现有终态优先级，避免重复完成或清理。
- 交接后，Parent Abort 不得错误地夺回所有权。
- 资源或清理失败必须通过仓库现有失败/诊断路径保持可见；
  不得静默遗忘活动资源。

使用一个由适配器拥有的命令截止时间，
保留现有前台默认值，以及后台和 yield 的显式超时/无超时规则。
在 SDK spawn 前、期间和之后跟踪停止请求；
取消后迟到的成功 spawn 必须被终止并完成终结，
然后才能释放所有权，且绝不发布。
不得让 SDK 调度器和适配器计时器独立终结工具结果。
Framework 截止时间仍是现有的外层执行边界。

原生启动期间的取消可能无法立即停止启动本身，
因为 SDK spawn 不接受 AbortSignal。
保留待启动所有权，直到原生调用拒绝，
或返回可被 kill 的句柄。
应显式测试此状态；
started Promise 被拒绝本身并不能证明不存在工作负载。

### 临时环境提案

使用位于 Agent Home 外、每次执行唯一创建的临时根目录，
以及最小 Windows/Node 环境。
将 SystemRoot、ComSpec、HOME/USERPROFILE、LOCALAPPDATA、
TEMP/TMP 和可信 PATH 准备保留为不可由调用级覆盖的项；
沙箱模式下显式拒绝冲突的输入项。
保留不改变保留引导配置的普通调用级环境变量新增项。

为初始无网络配置档设置离线 npm/cache/update-notifier 值。
绝不合并整个宿主环境，也不记录其值。
保留临时目录，直到工作负载树和原生资源释放完成终结；
Session 清理和 Host 关闭负责已交接命令的最终清理。

### 受隔离约束的 TEMP 引导程序

仅靠公开 SDK 请求无法保证私有 Windows TEMP 已就绪。
已测试宿主将 TEMP、TMP 和 LOCALAPPDATA
重写为每个沙箱随机路径，但不会创建这些路径；
预先创建 `Packages` 也未解决问题。
仅设置 TMPDIR 不会重定向 Windows Node 的 `os.tmpdir()`。

在 MXC 边界内选择一个小型可信 Node 引导程序，
使用与 Host 相同的 Node 运行时。
这是应用拥有的 JavaScript 入口，
不是新的原生可执行文件、sidecar 服务、后端或 SDK fork。
在实现并验证已接受契约前，
不得将一次性 Spike 脚本直接复用为生产代码。

1. Host 创建唯一空根目录，并将固定引导程序的绝对路径传给 SDK spawn。
   授予该入口只读权限，而非已安装应用的可写权限。
   保留原始 `cwd` 作为引导程序 cwd。
2. 在 wait 前连接 SDK 流。
   通过 stdin 传递一个有大小限制的私有 JSON 信封，
   包含未改变的命令和可信自有根目录；
   不将信封放入可执行文件 argv 或 Agent 提供的环境变量。
   发送前检查 Abort。SDK 启动本身绝不完成 `started`。
3. 将根目录绑定到保留的、由 Host 生成的引导环境值；
   即使另一目录可写，也拒绝指定该目录的信封。
   调用级环境不得覆盖此值，且在用户 Shell 启动前移除它。
   引导程序验证信封和根目录，
   然后在根目录内准备 Windows 重写的数据路径，
   以及稳定的 home/appdata/tmp/cache 目录。
   启动用户代码前拒绝根目录外路径、格式错误和 reparse 逃逸。
   后续清理仅针对原始自有根目录。
4. 将子进程 TEMP/TMP 和 LOCALAPPDATA
   设置为现已存在的自有目录，并显式设置离线 npm/cache。
   不修改宿主环境、机器权限或已配置的项目/内容授权。
5. 使用现有 `cmd.exe /d /s /c` argv 约定
   和 `windowsVerbatimArguments: true` 启动原始命令。
   不拼接准备命令、重写路径或重新解释用户命令。
6. 缓冲子进程 stdout/stderr，
   直到引导程序在实际 Shell spawn 后发出恰好一个有大小限制的启动帧。
   准备/spawn 失败发出失败，而非就绪。
   Host 消费并验证这一私有首帧，
   然后将后续每个字节视为普通命令输出；
   看起来像帧的用户输出不得触发新握手。
7. Shell 退出时传播其退出码、排空输出并关闭引导根进程，
   使原生 job 清理移除剩余后代进程。
   不得无限等待被后代持有的管道：
   任何输出排空截止机制都必须有界、明确且单独测试，
   不得静默丢弃数据。
   Abort/超时/手动 kill 和整树释放仍通过 SDK 终止操作完成。

原型验证了未改变的 cmd 命令、常规基于文件的 Node 临时文件创建、
离线 npm、命令启动前失败、精确的 512 KiB stdout / 64 KiB stderr 转发、
正常后代清理和显式 SDK Abort。
原型的排空截止分支未被执行；
其数值超时并不是已接受的生产默认值。
最终适配器/协议、reparse 防护、输出排空和已安装入口测试
仍是交付要求。

## 安全与能力

针对自有测试数据验证实际读取/写入/拒绝访问，
包括 reparse point 和隐式操作系统授权。
可读路径列表或单独使用 `realpath`
都不能证明预期边界。
只读访问仍可能暴露秘密；
最小可见性与防止写入是不同概念。

构造最小环境，不合并宿主整个 `process.env`。
使用独立临时数据，检查继承句柄和启动输入。
明确规定并验证网络拒绝；
不得将协作式代理变量或网络限速当作 deny-all 强制执行。

记录受支持的资源控制，
没有后端证据时不得声称存在 CPU、内存、进程或磁盘限制。
设计接受前必须确定所需限制；
缺少必要限制会阻止相应模式。

首个配置档仅声明文件内容访问限制、元数据策略、
外部网络拒绝和进程生命周期能力。
现有超时、托管容量和输出边界
不是每个沙箱的 CPU、内存、PID 或磁盘配额。
不新增资源限制框架，也不宣传这些尚未实现的保证。

对于首个无网络工具配置档，
显式选择自有工具缓存，并在支持时禁用工具更新检查，
而不是继承宿主设置。
Spike 的 npm 任务在离线模式、自有缓存和禁用更新通知的条件下，
通过了两次全新 home 测试；
未配置的任务发生了无法解释的冷环境超时。
不得通过延长截止时间掩盖这些失败，
或声称所有包管理器命令都能工作。

审查锁定发行版本的诊断和遥测。
仅使用测试数据的实验不授权传输项目数据或凭据。

## 兼容性与迁移

仓库当前要求 Node `22.x`。
默认候选方案迁移至受支持的 Node 24 LTS SDK 路径；
本草案不授权该升级。
必须验证 Node 24 原生扩展安装，
而不是复用 Node 22 二进制文件。
Spike 验证了全新 SQLite 12.8.0 Node 24 预构建版本；
已安装 Sharp/原生文件系统 smoke 检查也通过，
但这不等于完整应用回归。

明确关闭沙箱时保留宿主直接执行行为，
是候选的主动启用策略，而非自动失败回退。
现有审批契约保持不变。
未经负责人批准迁移/移除关卡，
不得引入临时双实现或依赖例外。

Windows 验证不能证明 macOS/Linux 支持。
在不支持的执行宿主上选择沙箱时，
不得静默使用宿主直接执行。

## 接受与验证

1. 使用精确产物和环境完成并审查 Spike 矩阵。
   缺失必需隔离/生命周期观察会阻止采用。
2. 接受绑定、所有权、配置和能力决策，
   并在 Delivery 前建立适用的持久 ADR/Spec 契约。
3. Delivery 检查覆盖新适配器行为和现有 Exec、
   Process 与审批回归；
   真实 Windows 测试验证约束与生命周期，
   包括启动失败和后代清理。
4. 运行适用的集成、lint/build 和已安装产物检查。
   仅对新的持久依赖不变量添加 Fitness 检查，
   不检查文档文字。
5. 对边界和生命周期变更进行聚焦的独立审查，
   并获得负责人接受；
   仅同步直接受影响的权威文档/指导。
